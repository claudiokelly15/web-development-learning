## 4. Proposed SE-1.0 representation

All names and rules below are **PROPOSED**. A later implementation must produce exact reviewed SQL and isolated constraint evidence before migration approval. These are logical requirements, not a claim that SQLite has already enforced them.

### 4.1 Foundation binding columns and guards

1. `users.email_binding_version INTEGER NOT NULL DEFAULT 1`: positive integer, no overflow/wrap, increment **exactly once per logical change** to the byte-exact stored normalized `email` or `email_verified_at` (including clearing verification and subsequent verification). No-change writes preserve it. Direct assignment, decrement/reset or version-only increment is denied. An address change must clear `email_verified_at` in the same write; a later verification of that address advances the version again. Future writers and framework verification must use one reviewed atomic path, or an engine-maintained increment trigger whose internal update is explicitly constrained. Do not combine both increment methods. The implementation proposal should select and prove the engine-maintained method; this document does not supply its SQL. Imported unchanged verified email may start at version 1 only after an explicitly reviewed trust/admission procedure; this does not manufacture a new verification event or automatically admit historical accounts to live submission.
2. `merchant_memberships.authority_version INTEGER NOT NULL DEFAULT 1`: same integer/overflow discipline. Advance exactly once when `role`, `status` or `revoked_at` changes, including revoke/regrant and downgrade/restore. Tenant/user/id are permanently immutable; a new logical relationship needs a new record under an approved lifecycle. Block DELETE/REPLACE of membership rows, so an epoch cannot reset by row recreation. This is preservation of authorization evidence, not legal proof of representation.
3. Existing `users.auth_version` must be monotonic and advance on security-relevant account suspension/closure/restoration and credential/session invalidation under the approved account policy. Add narrow guards and integrate writers before success is enabled; account-status toggling may not revive an old request/session. No assumption that current positive-integer checks already guarantee this.
4. Existing `merchants.profile_version` must advance exactly once on a change to any current stored business/profile field: business name/type, registration country/number, business email/phone, address lines, city, region, country and postal code. No-change writes preserve it; no decrement/reset or unchanged-version content edit. `id` and creator are immutable. Operational/verification status is handled by lifecycle authority, not disguised as a profile edit. This proposal adds enforcement, not a profile editor. The application draft's `profile_version` is synchronized to the freshly validated merchant version in the approved draft-preparation path; submission rejects disagreement and never silently updates stale input.

No current-user FK includes a mutable epoch: that would prevent legitimate later email/authority changes. Freeze the observed epochs in evidence, validate at insertion and compare against live state whenever current readiness is needed. Block user DELETE/REPLACE and ID reassignment in this profile as well, so recreating an account cannot reset epochs or reuse an authenticated identity; a future retention/purge lifecycle requires separate review. No new email-history table or membership grant UI is required for this package.

### 4.2 `merchant_application_submission_evidence` — one row per successful attempt

All columns are NOT NULL. There are no draft, pending or mutable completion flags on this table.

| Field(s) | Exact logical type and meaning |
|---|---|
| `application_id`, `merchant_id` | TEXT ULIDs using existing-parent byte/case compatibility; application ID is PK. Exact binary FK lookup; uppercase only for crypto canonicalization. |
| `contract_version` | TEXT constant `submission-evidence-v1`. |
| `actor_user_id`, `membership_id` | Positive INTEGER; submitting account and owner membership observed under the writer. |
| `auth_version`, `authority_version`, `email_binding_version` | Positive INTEGER snapshots of current security/authority/email epochs. |
| `attempt_number`, `profile_version`, `context_version` | Positive INTEGER; exact current application attempt, merchant/application profile and onboarding-context versions. |
| `identity_id`, `identity_version` | Existing identity ULID and positive logical version; declaration by this actor and this merchant. |
| `contact_id`, `contact_version` | Existing contact ULID and positive logical version; purpose fixed by `purpose`. |
| `purpose` | TEXT constant `application_phone`. |
| `proof_id` | Existing proof ULID, UNIQUE; no proof serves two applications. Challenge, policy and times are available through its frozen lineage. |
| `submission_request_id` | Canonical lowercase UUID; UNIQUE `(merchant_id, actor_user_id, submission_request_id)`. Opaque correlation token, never authorization. |
| `submitted_at_ms` | INTEGER UTC epoch milliseconds, 0..253402300799999; authoritative transaction time. |
| `submitted_at` | TEXT exact canonical UTC `YYYY-MM-DD HH:MM:SS.mmm`, length 23, valid Gregorian instant and exactly equivalent to `submitted_at_ms`. Same bytes in application and audit. No implicit Eloquent timestamp truncation. |
| `audit_event_id` | New canonical uppercase ULID, UNIQUE; matching `application.submitted` event. |
| `audit_event_type` | TEXT constant `application.submitted`, used in exact audit FK tuple. |
| `evidence_ciphertext` | TEXT canonical contextual AEAD envelope, byte length 1..16384, no NUL; protected capsule described below. |
| `evidence_key_ref`, `binding_key_ref` | TEXT key identifiers, 1..64 lowercase `[a-z0-9._-]`; no secrets. |
| `envelope_version` | INTEGER constant 1, identifying the new evidence-envelope contract; not permission to reuse the PD-03 phone/NIN purpose. |
| `retention_policy_version` | TEXT policy identifier, 1..50 printable ASCII `[a-z0-9._-]`; owner-approved policy must exist before live use. No guessed duration. |

All INTEGER columns require SQLite `typeof='integer'`, not affinity alone. Required TEXT has type/byte-length/alphabet/NUL checks; no NULL-passing tuple checks. Use parent-compatible ULID rules for existing IDs and accepted uppercase rules for new IDs. Versions never exceed signed 64-bit range; reject increment at its maximum.

The exact canonical protected payload has only these keys, in this order: `v` (1), `email` (fresh normalized submitting account address), `email_verified_at` (frozen verified timestamp in approved canonical UTC precision), `business_name` (fresh 1..200-character accepted name), `market` (`TZ`), `currency` (`TZS`), `identity_content_mac`, `contact_content_mac`. The two MACs are lowercase 64-hex HMAC-SHA256 values over the canonical decrypted logical NIN/phone plus their domain, merchant, record, actor and logical version, using the separate evidence-binding key. They stay **inside encryption**: they are not public identifiers or unkeyed low-entropy hashes. This detects logical-content substitution across permitted source-envelope rotation without copying a NIN/phone into a snapshot. Do not store ciphertext hashes as a substitute; legitimate rotation changes ciphertext bytes.

No optional profile data is frozen in v1 beyond the minimum business name. The frozen `profile_version` records which full profile version was consulted; it is not an archival copy of every optional field. A later review that needs historic optional values needs an expressly expanded allowlist/version. Missing registration/address/documents/bank details remains a non-blocker. No NIN, phone, OTP, password, token, IP, device fingerprint, internal review note or claimed independent identity match is allowed in the capsule. Membership/active account, syntax-valid declaration, verified email and phone possession are distinct facts; none asserts legal identity, regulatory compliance or merchant approval.

### 4.3 Referential integrity, insertion guards and immutable fields

Use RESTRICT deletion on all referenced evidence parents. No cascade deletes or ON UPDATE CASCADE. Add separately named UNIQUE indexes where the existing parent key is not already sufficient:

- Applications: `(id, merchant_id, submitted_by_user_id, submitted_at, profile_version, attempt_number)`.
- Memberships: `(id, merchant_id, user_id)`.
- Identities: `(id, merchant_id, declared_by_user_id, version)`.
- Contacts: `(id, merchant_id, actor_user_id, purpose, version)`.
- Proofs: `(id, merchant_id, actor_user_id, contact_id, purpose, consumed_application_id, consumed_at)`.
- Audits: `(id, event_type, actor_user_id, merchant_id, application_id, request_id, occurred_at)`.

Evidence FKs bind, respectively, its application/merchant/actor/submitted text time/profile/attempt; membership/merchant/actor; identity/merchant/actor/logical version; contact/merchant/actor/purpose/logical version; proof/merchant/actor/contact/purpose/application/submitted millisecond time; audit ID/constant event/actor/merchant/application/request/submitted text time. Add a direct user FK and merchant FK. Application, proof and audit final-tuple FKs are **DEFERRABLE INITIALLY DEFERRED with NO ACTION on UPDATE**, allowing the one transaction to establish them before commit; DELETE remains RESTRICT. Immediate RESTRICT update semantics must not be used on those deferred edges, or the insertion order will fail. The remaining edges can be immediate; referenced logical identity/version and consumption fields stay immutable. Later proof revocation preserves the consumption tuple, so it does not break historical FKs.

Required separately named guards:

1. Evidence INSERT: require current draft/current_slot=1, matching fresh owner/account/epochs, current context and exact current identity/contact/policy, valid available proof/lineage/times and no merchant R06 pending obligation. Reject pre-existing application evidence or conflicting audit event/request; derive the intended canonical audit fields from authoritative values. Inspect rows, not client assertions. Enforce all SQL-expressible equality/state/time rules; crypto, session, approved policies and trusted provenance remain service responsibilities. Validate the matching generated audit after the AFTER INSERT action and before commit.
2. Evidence UPDATE/DELETE: always abort, including same-value UPDATE, UPSERT conflict updates and replacement paths. Enforce replacement resistance with FK restrictions, recursive-trigger configuration/admission checks and explicit INSERT collision rejection; do not rely on ORM hooks. Cryptographic envelope rotation is not a generic UPDATE exception.
3. Proof transition available → consumed: require the preinserted matching evidence row and its exact consumption/application/time tuple; preserve all frozen C proof guards. Reject raw consumption with no evidence. Subsequent consumed → revoked retains the tuple and original evidence.
4. Application draft → pending_review: require exactly one matching evidence row, correctly consumed proof and exact redacted audit, and equality of submitted actor/time/profile/attempt. Prohibit non-draft INSERT, draft submission-field fabrication, non-draft → draft revival, and modification of application identity/attempt or frozen submission fields once evidence exists. Preserve later accepted review states without adding decision permission. Never mutate merchant financial/verification/operational status as a submission side effect.
5. Application evidence-less historical non-draft rows remain legacy history. Freeze their existing submitted fields; never backfill invented proof/email evidence, admit them as SE-1.0, or silently rewrite them into draft. New non-draft writes must use SE-1.0. Draft deletes that could reset an application/request identity are denied; future archival/reapplication needs its own reviewed lifecycle.
6. New `application.submitted` audit INSERT must require a current draft, valid actor/merchant/version/request shape and its matching already-inserted evidence row. The service creates the audit **from an evidence AFTER INSERT trigger**, using the evidence's frozen event ID and canonical payload. The deferred evidence-to-audit FK allows that ordering. The AFTER INSERT trigger inserts that exact audit; an audit BEFORE INSERT guard matches its fields to the evidence. If either action fails, the statement and transaction fail. There is no direct service success-audit insert and no auxiliary audit table. Existing historical audit rows are preserved; new raw orphan success-audit INSERTs fail. A complete success is accepted only through the matching evidence/application/proof/audit bundle.

Rule 6's trigger-generated audit is the **selected v1 design**. This explicit ordering avoids an impossible immediate circular dependency: evidence first, its trigger-generated audit second, consumption and application transition next, deferred validation at commit. FK/recursive-trigger enforcement and exact amendment object definitions are readiness prerequisites. A single autocommit evidence INSERT fails its deferred final-state bindings.

These guards stop unauthorized row mutation with the approved schema intact. They cannot stop a database administrator who disables FKs, drops triggers, replaces files or possesses application keys. Exact schema admission, file/key custody and restore/replay holds are independent requirements; no SQLite design here claims tamper-proof storage against that principal.

## 5. Encryption, retention and lifecycle

**Proposed evidence cipher:** reuse the accepted sodium XChaCha20-Poly1305 primitive, random 24-byte nonce and strict canonical envelope approach; create a separate evidence service/domain and bounded payload parser. PD-03 `VerificationCipher` currently accepts only phone/NIN domains and short payloads, so do not pass the new payload through it or relax its existing purposes/limits. Use dedicated 32-byte `submission_evidence` and `submission_binding` keys, independent of APP_KEY and all four verification domain keys. No keys are generated/provisioned by PD-04B.

Evidence AEAD associated data uses the accepted length-prefix encoding with domain `xlipa-submission-evidence-v1`, deployment namespace, algorithm, envelope version, both key references, and **every typed evidence field except the ciphertext itself**, in the table order above. Integers use canonical unsigned decimal text; ULIDs use local uppercase crypto copies while binary FK values remain authoritative. Bind the protected payload to the whole typed record, not self-reported envelope headers. Strictly reject unknown/duplicate keys, noncanonical encodings, oversize values, failed MAC/decrypt or unavailable keys. Neither HMAC nor AEAD creates provider provenance or independent identity verification.

All evidence columns/envelopes are immutable in v1. Retain necessary decrypt/binding key versions under protected custody for the approved retention period. KEK wrapping rotation may occur in a separately protected key registry without changing this row; data-key/envelope migration requires a later reviewed append-only envelope representation or amendment. Do not silently rewrite evidence or freeze source envelope revision as logical identity. Existing identity/contact envelope rotation must preserve decrypted content and be checked against the protected content MACs before any subsequent evidence-dependent use.

Owner must approve retention duration, lawful purpose/notices, subject-access/redaction procedure, hold authority and deletion method before live collection/submission. `retention_policy_version` freezes the policy used, not a statutory conclusion. Do not assume indefinite retention or invent a number of years. Legal/security holds and expiry scheduling need separately maintained operational records; no mutable hold flag is smuggled into immutable evidence. Existing identity `retention_due_at` must not schedule destruction earlier than required by referenced approved evidence policy/holds. No automated delete is enabled. A future authorized purge must address RESTRICT references, key erasure, backups and immutable history through a separately reviewed lifecycle; disabling triggers or cascading deletes is not an implementation shortcut.

Later email/account/owner/contact/identity/profile changes never rewrite the historical submission. They invalidate current decision/readiness when a frozen version/content/binding differs, even after change-away/change-back. Proof expiry after successful consumption does not erase the fact that it was valid at submission, and does not automatically approve later use. Pending review is not a transferable verified-merchant flag. Any new submission uses a new approved attempt and fresh proof. Suspension, restore, missing evidence keys, policy retirement, unresolved R06 and unverifiable lineage impose a current hold; restoring values or clearing a session flag cannot revive readiness. Review and resubmission actions remain separately gated.

## 6. Successful submission transaction — proposed implementation protocol

No success code is implemented here. Future input allowlist: expected application ID, attempt number, merchant/application profile version, context version, identity ID/version, contact ID/version, proof ID, email binding version, authority version, auth version and submission request UUID. Values are expectations, never authority or writeable server evidence. Do not accept NIN/email/phone/status/provenance/audit payloads in this endpoint. Use existing CSRF/private headers/throttles and current session authentication. No broad optional fields are required.

1. Acquire the existing Laravel-managed SQLite writer before workflow state reads. Reject ambient/nested transactions; bounded lock-acquisition failure returns retryable unavailability before work. No whole-operation retry after work begins, no reconnect/retry inside it and no external calls. Check FK/recursive-trigger enforcement, exact original C objects plus SE-1.0 manifest/ledger, operational processing/key/time/restore readiness.
2. Reload active verified account and exact session `auth_version`; reload active owner membership with null revocation and matching authority epoch; deny manager/staff/platform bypass. Validate market/purpose and current merchant not suspended/closed. Validate request UUID and check existing authorized outcome as described below before requiring still-available proof.
3. Reload exact current draft, attempt, merchant/application profile versions, context, identity/contact expectations and email epoch. Reject any mismatch with 409; never silently substitute the latest proof/contact or update a stale draft. Freeze the business name from authoritative current data; reject invalid supplied/current values under the approved minimum-field policy.
4. Reload and decrypt current identity under its true PD-03 binding; require exact declaring actor, logical version, supported claimed capacity and current approved syntax/declaration/notice policy identifiers, time and affirmative declaration provenance. Revalidate normalized logical content under the approved syntax service without a new identity match. Membership is not proof of legal representative authority; missing approved policy/processing authority fails closed.
5. Reload/decrypt exact current application contact; validate target/fingerprint and domain-key references. Require selected proof `available`, unrevoked/unconsumed, exact actor/merchant/contact/purpose/policy; `verified_at <= transaction_time < expires_at`, no grace. Require frozen `provenance='live'`, consumed matching challenge, SMS channel and accepted matching live delivery intent with valid original dispatch lease/acceptance chronology. Admit lineage only from the separately approved trusted live adapter/issuance path. Labels alone, simulated proofs, unknown/late delivery and provider acknowledgement without code verification are insufficient. No live adapter/API is specified here; unsupported provenance admission keeps submission disabled.
6. Require no unresolved R06 obligation anywhere in the merchant's applicable verification history; do not reconcile/force-clear as part of submit. Trusted time must not precede relevant context/limit/verification observations; clock or restore uncertainty is a hold. Read time once at the final validation boundary; if encryption/work delay reaches proof expiry before consumption, refresh/revalidate time and rebuild the proposed record consistently before any write. Freeze one time for consumption/evidence/application/audit.
7. Construct server-only typed evidence/canonical capsule and content MACs. Decrypt-check the resulting envelope internally before writing. Insert evidence while application is draft and proof is available; its AFTER INSERT trigger writes the exact redacted audit. Deferred FKs allow the final application/proof tuples to be established later **within this transaction only**. No evidence is visible to other normal connections before commit.
8. CAS consume exactly that proof: available/unrevoked/unconsumed and expected `state_version` → consumed, `state_version+1`, `consumed_application_id`, `consumed_at=submitted_at_ms`. Require affected count 1. No challenge re-consumption, new proof or counter reset.
9. CAS application from current expected draft/version/attempt to `pending_review`, submitted actor and canonical text time. Preserve current_slot=1 and same attempt/profile version. `profile_snapshot` remains NULL for new SE-1.0 submissions; the new protected capsule is authoritative. A draft with unrelated pre-existing snapshot content is held for explicit conversion review rather than overwritten. Require affected count 1. No merchant approval/status/financial side effect.
10. Recheck exact evidence/proof/application/audit agreement and pending/time/authority conditions needed at the final boundary, then commit once. Trigger/audit/decrypt/CAS/constraint/commit failure rolls back all transactional writes or produces an **unknown outcome** requiring resolution, never a claimed rollback if commit acknowledgement is uncertain. Send no notification/provider request in this transaction; v1 adds no after-commit delivery dependency.

The redacted audit is exactly: generated `id`, `event_type=application.submitted`, actor, merchant, application, same UUID, `target_user_id=NULL`, canonical submitted text time, and canonical metadata `{"from":"draft","to":"pending_review","profile_version":N,"reason_code":"minimum_evidence_bound"}` in that order with integer N. Existing metadata allowlist/2048-byte bound suffices. No email, identity/contact value, content MAC, key ID, OTP, token or fingerprint in audit. Evidence/audit IDs and versions are private metadata; no new generic reveal or audit browser is authorized.

### Duplicate, concurrent and unknown-outcome rules

- Same merchant/actor/request UUID and identical frozen expected tuple: after fresh read authorization, return the existing safe submission receipt when the complete bundle validates. Do not consume again, create a second audit or demand that an already-consumed proof still be available. Later expiry/revocation means current readiness may be held; receipt reports the historical committed event only.
- Same UUID with different expected tuple, actor, or application: conflict/tenant-safe denial, no writes. Different UUID for an already-submitted attempt: 409 with authorized current status, not a second successful command. A token is never used to discover a foreign outcome.
- Competing requests serialize at writer acquisition. One valid winner may commit; the loser reloads and receives identical-outcome receipt only for the same UUID/tuple, otherwise conflict. UNIQUE application/proof/request and CAS plus FKs remain backstops. Contention before acquisition may be retried as a new request using the same UUID.
- Connection loss/exception during COMMIT: return “outcome not confirmed,” suppress automatic retry and discard/quarantine that connection. On a fresh trusted connection with all normal authority/schema/restore checks, resolve the same UUID against the entire bundle. Present success only if all fields, AEAD, audit and consumption validate. No record on an authoritative, recovered current database permits an explicit replay of the **same** UUID/expectations; a stale backup/read replica cannot establish absence. Partial/conflicting records imply integrity hold, never repair by inventing evidence or new success audit. No background replay worker is introduced.
- Revoked owners cannot use idempotency lookup as an access bypass. An authorized successor may see normal redacted history under its policy, but cannot impersonate the original submitter or replay their command. Browser button state never decides success.

## 7. Amendment, compatibility and implementation scope

**Proposed future sequence:** approve this logical contract/owner decisions → produce exact SE-1.0 SQL/manifest and fixture-only migration tests → review that concrete diff → separately approve application implementation and fixtures → separately approve any operational release/working migration. No phase authorizes the next.

The new migration must require exact accepted C schema/ledger and idle managed connection, validate existing rows without adopting incompatible history, and add only the table, two columns and listed amendment-owned indexes/triggers. Use a new identity/version/ledger name, never edit/reuse the C artifact, synthetic migrations or their manifests. No inferred evidence backfill, phone/email promotion or proof fabrication. Pre-existing rows get structural epoch defaults only; existing historical verification trust requires the explicit admission decision in section 8. Inconsistent/oversized/noncanonical data or conflicting objects abort with no partial amendment.

New indexes on C tables and triggers referencing them are **additional SE-1.0 objects**, not modifications to their frozen CREATE TABLE/index/trigger definitions. This is a new operational schema profile; it is not covered by historical C-only acceptance. Current PD-03 readiness verifies named C objects but does not certify all new objects or lifecycle enforcement; add a separate composed submission-readiness service and exact allowed-object manifest. The original C selector expects the old foundation, and must not be rerun against an amended database. Fresh setup applies C first, then independently selected SE-1.0. Any manifest/source-pin release changes require their own approved tooling package without rewriting accepted historical artifacts.

Rehearse failure after every DDL/data-copy/ledger boundary in generated fixtures. Preserve all existing IDs, ciphertext bytes, schema definitions, indexes/triggers, audit rows and migration records.
